# 补充资料与字段匹配设计

文档版本：1.1 · 2026-09-11  
关联主计划：[纯插件版产品研发计划](纯插件版产品研发计划.md)  
状态：已确认本地补充资料表和首版本地字段匹配；按后续决定，模型辅助模糊字段匹配也升为 P0。本文定义统一资料与匹配契约，模型设置、直连及发送约束见[模型 API 专项设计](纯插件模型API与模糊字段匹配.md)。完整产品功能尚未实现。

## 1. 本轮决定与首版边界

简历、Markdown 原文和补充资料均保存在当前浏览器的插件本地存储中，随完整备份迁移。用户自行向外部 AI 上传简历，以及用户确认将字段填写到招聘网页，是各自独立的操作。“本地保存”描述插件的数据存储位置，不表示外部 AI 或招聘网站从未接收过用户提供的资料。

| 本轮确认 | 首版落地 |
| --- | --- |
| 简历之外的必要信息也需要维护 | 增加“补充资料”表，手动新增、编辑、删除和保存 |
| 先做字段匹配 | 复用现有本地规则，补稳定字段定义、明确别名、分组约束和手动来源选择 |
| 模型 API 模糊字段匹配升为 P0 | 本地与模型提供器共用匹配接口；DeepSeek Anthropic 作为首轮实测基线，支持其他兼容提供商 |

首版对规则无法确定的表达提供模型辅助候选，保留无法判断和手动选择。增加用户模型 Key 设置及按域名授权，扩展直接请求所选提供商；无业务后端或账号依赖。记住某网站的手动对应关系仍列为后续增强，首版手动选择只作用于本次扫描会话。

## 2. 补充资料表

在资料页增加“补充资料”入口，表中显示资料名称、内容、含义说明与编辑操作；内部字段标识无需用户填写。首版建议支持短文本、长文本两种内容类型，使用已有普通文本框、textarea、原生 select/radio 的填写能力。下拉或单选仍要求内容与网页选项唯一对应；日期控件和其他复杂控件不能仅因保存了文本就宣称支持。

提供可选的空白常用条目，也允许新增自定义条目。以下是建议初始条目，均由用户填写，不生成默认事实；实际可用程度由目标网页验收决定。

| 资料名称 | 含义和示例用途 | 与已有信息的关系 |
| --- | --- | --- |
| 籍贯 | 用户自己确认的籍贯 | 独立于现居城市、户籍所在地、生源地 |
| 户籍所在地 | 用户自己确认的户籍所在地 | 不从籍贯或现居城市推断 |
| 生源地 | 按目标申请要求填写的生源地 | 不从学校所在地推断 |
| 期望工作地点 | 用户明确的地点偏好 | 独立于现居城市 |
| 语言成绩说明 | 用户填写的考试、分数和时间说明 | 可填说明文本框，拆分成绩控件另行适配 |
| 到岗时间说明 | 用户明确的到岗安排 | 首版按文字填写，不从毕业时间推算 |

已有姓名、手机、邮箱、学校等资料直接使用其现有来源；不再创建一份同义副本。自定义项与已有来源同名或含义重复时，提示改用现有字段；允许保留的不同含义条目要写清名称和说明，发生歧义时不能自动选一个。

工作、教育、项目等重复经历继续使用原有分组表单。补充资料表用于额外的个人信息或偏好，首版不把它扩展为任意关系表或替代已有经历管理。空值表示未提供；同名项、缺少名称和超长内容有明确校验。建议上限 100 项、名称 80 字符、说明 300 字符、单项内容 6000 字符，同时服从正式资料 1 MiB 与本地总容量预算。

用户维护或从原文复制的内容，需要点击“保存资料”后才参与填写。沿用项目已有的受限字段处理，不借自定义条目绕过密码、验证码、证件号、银行卡和协议等限制。

## 3. 数据、导入和备份

在拟升级的 Profile 1.1 中增加 `supplemental_fields`，保存为 `activeProfile` 的一部分，复用同一正式修订、草稿、上一份和保存冲突机制。每个条目包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定条目 ID，排序和改显示名称时保持不变 |
| `field_key` | 稳定的语义标识；预置项如 `supplemental.native_place`，自定义项由程序生成 |
| `label` | 用户看到的资料名称 |
| `description` | 用户补充的含义说明，不作为填写值 |
| `value_type` | 首版 `text` / `multiline` |
| `value` | 已确认字符串或 `null`，后者不参与填写 |

条目 ID 全局唯一；预置 `field_key` 同一简历内只能出现一次。改名称不改变字段含义或内置别名；若含义变化，创建新项并删除旧项。旧 1.0 资料迁移时新增空数组，不从姓名、地址或经历猜出这些值。

Markdown 的 `resume-md/1` 仍只定义简历章节。解析器输出的是简历候选，不拥有补充资料表；导入应用层以当前编辑草稿为基础，替换简历章节并保留其 `supplemental_fields`。修改 Markdown、表单或补充资料后，旧候选应用预览失效，避免套用预览期间已经过时的值。导入界面明确显示“更新简历内容，保留补充资料”。

Markdown 中的“补充信息”是保留原文的栏目，用户可以查看并复制到补充资料表；首版不自动将其中任意文字变成字段或事实。“补充信息”与可用于填写的“补充资料表”在界面上分别说明用途。

完整 JSON 备份、正式资料上一份和草稿均包含补充资料。导入旧 1.0 简历 JSON 时，使用与 Markdown 相同的范围，保留当前补充资料；迁移到全新安装时默认无补充资料。恢复新版完整备份则在预览中单独列出补充资料的新增、修改、删除，按用户确认的完整恢复范围处理。资料删除、清空或恢复必须更新正式修订，使已有填写预览失效。

“导出当前简历 Markdown”继续输出简历支持字段和原文中保留的补充信息，默认不额外附上手工维护的补充资料表；导出界面写明这个范围。补充资料随完整 JSON 备份迁移。模板不因此增加会被外部 AI 重写的私人信息字段；后续若增加补充资料的 Markdown 导入导出，需要另定可往返的模板版本。

## 4. 公司更换字段名称时的匹配方式

同一项资料使用稳定的语义标识，网页上的字段名称通过别名关联。资料值不以某家公司表单标签为存储键；换公司无需重新录入同一份值。

| 网页字段 | 本地资料 | 处理 |
| --- | --- | --- |
| 手机号 / 联系电话 / 手机号码 | 手机 | 明确别名在相容分组中匹配 |
| 毕业院校 / 学校名称 | 某段教育经历的学校 | 先确认教育分组，再绑定具体经历 |
| 当前居住地 / 现居城市 | 现居城市 | 只采用已定义、含义一致的别名 |
| 籍贯 / 户籍所在地 / 生源地 | 三个独立的补充字段 | 不相互替换 |
| 名称 / 地点 / 日期 | 尚不明确 | 显示候选或未匹配，让用户选择 |

执行顺序：

1. 先识别受限字段与不支持控件，这些不能被规则、手选或未来模型绕过。
2. 利用页面已有的字段标签、分组、控件类型和明确语义属性，查找经过验证的站点规则、标准字段名及别名。
3. 有明确分组冲突时拒绝跨组候选；不能因为全局只剩一个同名字段，就把它填到错误的分组。普通“姓名”还需区分申请人、联系人等上下文。
4. 对多段教育、工作、项目要求具体条目绑定；多个候选显示待选择，未知或缺失值留空。
5. 对未识别或歧义名称，用户可在确认发送内容后请求模型给出候选，也可直接从已保存资料中选择来源，并检查内容是否适合当前控件。自定义项缺少明确含义时保留待选择，不让模型编造对应关系。
6. 所有建议进入统一填写预览，显示来源、实际值与匹配依据。用户确认后再写入、回读并报告结果。

本地规则不做任意字符串的模糊相似度自动配对；陌生表达通过 P0 模型辅助提供待核对建议，也不将每次手动选择变成全网站别名。网页字段匹配与 Markdown 解析是两套职责；增加网页别名不能改变解析器的输入语法。

后续若支持“记住这个网站的对应关系”，以站点、表单结构、分组和控件语义限定作用范围，保存来源标识而不是旧资料值。页面结构变化、来源删除或歧义出现时重新确认；不能只凭域名复用到该招聘系统托管的所有公司。

## 5. 本地与模型匹配的统一接口

将现有 `rules.ts` 的字段来源识别抽为 `FieldMatcher`，首版实现 `LocalRuleMatcher` 与 `ModelFieldMatcher`。这里定义内部 TypeScript 契约，模型通过专门的协议适配器直连提供商，不新增业务 HTTP 路由。接口采用异步签名并支持取消任务。

```typescript
interface MatchFieldDescriptor {
  fieldId: string;             // 本次扫描的临时标识
  groupId: string;             // 本次扫描的分组，用于查找经历绑定
  label: string;
  groupLabel: string;
  section: string;
  kind: string;
  optionLabels: string[];
  blocked: boolean;
}

interface MatchSourceDescriptor {
  sourceRef: string;           // 引用正式资料；不包含资料值
  fieldKey: string;            // 稳定语义标识
  label: string;
  description: string;
  section: string;
  recordId?: string;           // 重复经历标识，不含学校或公司名称
  hasValue: boolean;
}

interface FieldMatchRequest {
  requestId: string;
  siteContext: { origin: string; formType?: string }; // 本地规则上下文，无查询参数
  profileRevision: number;
  pageToken: string;
  scanRevision: number;
  selectionRevision: number;   // 用户来源选择变化时，旧结果失效
  providerRevision?: number;   // 模型请求必须携带
  disclosureRevision?: number; // 用户核对的实际发送内容修订，模型请求必须携带
  fields: MatchFieldDescriptor[];
  sources: MatchSourceDescriptor[];
  bindings: Record<string, string>; // groupId + section → 经历 ID
}

interface FieldMatchResult {
  requestId: string;
  profileRevision: number;
  pageToken: string;
  scanRevision: number;
  selectionRevision: number;
  providerRevision?: number;
  disclosureRevision?: number;
  decisions: Array<{
    fieldId: string;
    status: 'matched' | 'ambiguous' | 'unmatched' | 'blocked';
    candidates: Array<{
      sourceRef: string;
      evidence: 'site_rule' | 'exact_label' | 'alias' | 'model';
      reason: string;
    }>;
  }>;
}

interface FieldMatcher {
  match(request: FieldMatchRequest, signal?: AbortSignal): Promise<FieldMatchResult>;
}
```

`matched` 只表示来源唯一对应，不等于值可以填写或已经填写成功；仍需解析本地值、检查网页选项、长度、分组与用户确认。手动绑定是会话内的用户操作，经过同一来源校验和预览流程。

匹配器不返回填写值、CSS 选择器、JavaScript 或 DOM 操作。调用方验证请求标识和全部修订、候选是否存在、结果字段是否重复、状态与候选数量是否一致；`matched` 必须恰好一项候选，`ambiguous` 至少两项，`unmatched` / `blocked` 不带候选。失效、格式错误、越界或被取消的结果不可用于生成操作。

P0 的 `ModelFieldMatcher` 只处理用户选定的本地未匹配或歧义项，提供相同格式的候选建议。外发适配层另行构造经过用户核对的最少字段描述和匿名来源目录，不直接序列化 `FieldMatchRequest`：即便无资料值，网页分组文字、自定义名称和说明仍可能带有个人内容。只发送处理所需信息，临时代号、请求修订与内部标识的对应关系保留本地；收到响应后由适配层回填本地修订，不让模型生成这些控制字段。

模型失败或超时后继续显示本地结果和手动选择；模型不能修改正式资料、绕过分组或执行填写。首版发布包包含两种协议的模型提供器，但不包含 Key 或测试替身。具体配置、权限、请求预算和真实测试按[模型 API 专项设计](纯插件模型API与模糊字段匹配.md)实施。
