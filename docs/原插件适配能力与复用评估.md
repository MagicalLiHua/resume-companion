# 原插件适配能力与复用评估

检查日期：2026-09-10。对象为本机提取的求职方舟 `2026.9.9` 发布包。

结论：**已经有可供研究和迁移设计的网站适配逻辑，不需要把每种控件的处理方式都重新摸索一遍；但不能仅复制前端或替换服务域名，就继承原产品的全部网站支持能力。** 直接复制业务代码还缺少明确的许可依据。本次只进行静态检查和规划调整，没有执行原插件，也没有访问其登录后接口。

## 1. 检查范围与证据强度

- manifest 实际加载的是原发布包中的当前压缩脚本（本地研究材料，未纳入本仓库）。
- 原发布包中的旧版可读脚本用于理解函数和标注行号（本地研究材料，未纳入本仓库）。
- 对平台路由、企业页面预处理、特殊日期和主要远程接口，已在当前脚本中交叉确认对应逻辑。
- 旧版并非当前脚本的完整可读副本。当前脚本还包含 `chooseModalOption` 远程选项判断，不能只看旧文件就认为完成了当前版本的全部分析。
- 这是代码中存在相应处理的证据，不是这些网站目前都能成功填写的运行测试结果。

| 国聘 | `c.iguopin.com`，`/apply` 或 `/resume` | 栏目定位、单段/多段区分、字段识别、经历操作 |
| 智联校招 | `xiaoyuan.zhaopin.com`，`/scrd/` | 平台栏目、当前栏目与字段处理 |

因此，“许多企业网站可填写”不一定来自一个庞大的逐站规则文件夹；这份发布包采用的是**通用页面/控件处理 + 少数平台专用分支 + 服务端语义判断**。

## 3. 哪些能力依赖原厂后端

| 接口 | 插件发送/接收什么 | 脱离原服务后需要补齐什么 |
| --- | --- | --- |
| `getNeedField` | 发送整理后的页面内容，接收字段定义 | 本地字段解析或自己的字段理解接口 |
| `fillResumeValue` | 发送字段、简历等，接收拟填写值 | 本地结构化取值与自己的辅助生成 |
| `fillBlockResumeValue` | 按栏目生成拟填写值 | 分组绑定、重复经历与取值规则 |
| `getBlankItem` / `saveBlankItem` | 控件指纹与候选项缓存 | 自己的本地缓存或实时探测；拿不到原服务器缓存数据 |
| `chooseModalOption` | 当前脚本发送弹窗内容、上下文和简历片段，取得候选点击引用 | 本地可控选项匹配或自己的受限模型判断 |

字段识别、整页生成和分组生成请求均已在本地研究材料中核对，原文件未纳入本仓库。

服务端源码、提示词、训练/缓存数据、字段知识库和实际兼容性测试均不在发布包内。不能从这些请求反推出原厂具体采用了哪些内部实现。

## 4. 技术上如何利用现有成果

| 内容 | 利用方式 | 必须处理的事情 |
| --- | --- | --- |
| 平台域名、页面类型和栏目结构线索 | 用于确定适配对象与调查顺序 | 在当前页面重新验证 |
| 控件发现、可见性、事件触发、日期弹窗的处理思路 | 转成自己模块的需求与测试案例 | 区分通用规律和脆弱启发式 |
| 明确有复用许可的独立模块 | 按许可条件迁移或从上游引入 | 解耦全局状态、补错误处理与验证 |
| 尚未确认许可的业务实现 | 保留分析记录，按所需行为自行实现 | 不假定代码可读就是开源授权 |
| 账号、会员、原厂 API、智能学习与上传 | 不作为新产品依赖 | 使用本项目的数据和网络协议 |

原脚本不是可直接 `import` 的独立适配器包：栏目扫描、弹窗、全局状态、网络结果和简历全文相互耦合。即使之后获得复用许可，也需要拆分与联调，无法只复制几个函数就保证行为等价。

### 不应照搬的具体行为

1. 智联部分报名表的预处理会逐个点击 `.deleteBtn`，删除已有经历。这在当前运行脚本中也存在。新版本不得把“清空经历”当作扫描的一部分。
2. 前程页面有从简历全文搜索“博士/硕士”等关键词推测最高学历、否则默认本科的代码。新版本必须取用户确认的结构化事实，缺值则等待用户处理。相关原代码仅作为本地研究材料，未纳入本仓库。
3. 当前脚本部分日期逻辑会将只有年月的日期补为 `01` 日。新版本不自动创造用户未提供的日期。
4. 原流程发送页面内容、简历全文和当前字段值的方式，与本项目既定的数据最小化协议不同。复用控件经验时应同时替换这部分数据流。

## 5. 许可核对结果

发布包顶层只有 manifest，没有业务代码的 `LICENSE`、完整构建工程或官方源代码仓库声明。在业务脚本中也未发现明确的复用许可。

包内确有第三方开源组件声明：SimpleMDE 标注 MIT；Font Awesome 文件头分别说明图标、字体和代码许可。**这些声明只涉及相应第三方组件，不能作为整个求职方舟业务代码的许可。** 如新工程需要这些组件，应从各自上游引入并保留相应声明。

本次还检索了公开仓库线索，并查看[产品官网](https://www.qiuzhifangzhou.com/)，未确认业务代码的官方公开仓库或复用授权；官网页面未提供可读取的条款正文，因此不能把检索无结果视为确定不存在许可。

当前能确认的是技术结构和文件内声明；不能据此认定已经获得复制并分发业务代码给同学的许可。计划默认自行实现业务模块。若之后找到适用许可或作者明确授权，再评估直接迁移能减少多少工作。

## 6. 对开发计划的调整

- 先从已有平台分支和通用控件处理建立适配清单，减少重复摸索；不要求用户此刻凭印象决定两个网站。
- 初次真实验收仍选择两个具有代表性的流程，用来控制验证工作量；**两个是首轮验收样本数，不是产品支持数量的上限**。
- 首批候选从已确认分支的国聘、智联、前程/应届生中选择，结合实际可进入的页面和用户需求决定顺序。
- 不把静态发现的所有域名列入“已支持”清单，不假设网站当前实现仍与发布包适配代码一致。
- Word/PDF 自动导入暂缓；AI 问答与润色在本地填写之后处理。
- 当前工作仍属方案审阅与源码评估；没有开始产品实现。既有投入估算暂不因“看到适配代码”就下调，待真正解耦/自行实现并验证后再更新。
